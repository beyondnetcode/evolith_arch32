# Launch GO/NO-GO — decided 2026-08-16

The visibility plan puts one gate in front of the single act of promotion: re-run the
clean-room verification against whatever is published *today*, and write the decision down with
a date, before the morning of the launch rather than on it. This is that decision.

**Verdict: NO-GO.** The artifact passes. Distribution does not. The launch does not happen
until the gates in section 4 are green, and the specific reasons are below so that a later
reader can check whether they were good ones.

---

## 1. The artifact — GO

Re-run today in a container with nothing but Node, against the currently published
`@beyondnet/evolith-cli@1.3.0`. Not the W3 capture replayed: a fresh run, because
`@beyondnet/evolith-core-domain@1.3.1` reached the registry at 00:26 today and the CLI floats
`^1.3.0`, so the artifact a stranger installs this evening is *not* the one W3 verified.

```
npm install -g @beyondnet/evolith-cli@1.3.0
evolith init --name sat2 --yes
evolith validate --engine opa
```

Resolved: `core-domain 1.3.1`, `infra-providers 1.2.0`, `sdk 2.0.0`, `agent-runtime 1.2.0`.

| gate | required | measured |
|---|---|---|
| a real verdict, not `OPA policy not compiled` | yes | yes — 72 issue rows |
| exit code on a blocking verdict | non-zero | **2** |
| any Spanish in the output | none | none: the only non-ASCII are box-drawing, an em dash and `❌` |
| counts | reproducible | 133 checked / 26 skipped / 0 errored / 159 total |
| blocking accounting | reproducible | 37 blocking of 72 rows; 9 of them skipped |

Identical to the W3 capture on every number. The README's quoted block, corrected today to be
the tool's literal output rather than a paraphrase of it, still reproduces.

**One caveat, recorded because it is luck rather than design:** the published CLI floats
`^1.3.0` / `^1.2.0` on its two Evolith siblings, so publishing a sibling patch silently changes
what a fresh install resolves. The numbers survived this one. Nothing guarantees the next.

## 2. Distribution — NO-GO, 1 of 5

Measured today, not inferred from what was merged:

| door | check | result |
|---|---|---|
| GitHub Marketplace | `curl` the listing URL | **HTTP 404** |
| MCP registry | `?search=evolith` | **`{"servers":[],"metadata":{"count":0}}`** |
| GHCR anonymous pull | `/v2/.../tags/list` on three images | **HTTP 401** on all three |
| Claude Code plugin marketplace | `.claude-plugin/marketplace.json` on `main` | **present and valid** |
| third-party lists | backlink PRs opened | **0 of 4** |

The plan's own W5 tripwire reads: *if Marketplace is still 404 and the registry still returns
`{"servers":[]}`, half of distribution is dead no matter how good the README is.* Both are true
today.

Three of the four dead doors cannot be opened from here — they are a Marketplace publish button
on a Release, three GHCR visibility toggles in org settings, and an npm token with write
permission. The files, manifests and workflow jobs behind all three are written, merged and
verified. **They are waiting on clicks, not on work.**

## 3. The release train — NO-GO

The reason the MCP registry is empty is not that the job was never written. It is that
`publish-mcp-registry` has never successfully executed, because the release it hangs off keeps
failing. GT-705 — the fix that makes the published MCP server carry its own corpus — has now
failed to reach npm three times:

1. Blocked by the planner's version idempotency; solved by the patch bump in #570.
2. Blocked at `infra-providers@1.2.1`, whose shipped `dist` imports
   `@beyondnet/evolith-contracts/ingest`, a subpath the published contracts 1.1.0 does not
   carry. Fix merged to `develop` (#576), not yet on the registry.
3. Would have been "solved" into something worse: `@beyondnet/evolith-mcp@1.3.2` packs with
   **zero `dist/` files** — corpus and no code — and the job that reports the packlist asserts
   nothing about it. Caught in #580, before it shipped, only because the run failed at step 2.

Two further defects found the same day and fixed: `server.json` would have registered the MCP
listing against a version npm does not hold (#574, promoted in #577), and the guard meant to
prevent that was reading `package.json` while the publisher reads `server.json`.

**A launch post whose first line is an install command must not go out while the release train
is in this state.**

## 4. What has to be true before this is re-decided

1. `npm view @beyondnet/evolith-mcp version` returns a version whose tarball contains
   `dist/main.js` **and** `rulesets/`. That is GT-705 actually reaching users.
2. Doors at **3 of 5 or better**, with Marketplace and the MCP registry among the live ones —
   the Show HN post offers three install paths and two of them are currently dead links.
3. The clean-room verification in section 1 re-run against whatever is published at that
   moment, not replayed from this document.

## 5. What this changes in the schedule

Per the plan's own instruction for a failed GO/NO-GO: the promotion moves out a week and the
freed week becomes a fixing week. That is what today already was — four release-path defects
found and four fixed — so the schedule is being honest rather than slipping quietly.

Nothing about the post itself is blocked: the draft, its title, its opening comment and its
three install snippets are written and are not the constraint.

## 6. The rule this document exists to enforce

The plan says the decision is written while the outcome is still unknown, so that it cannot be
rationalised afterwards. The temptation being guarded against is specific and worth naming: the
artifact passed, the README is good, the post is drafted, and it would feel productive to ship
it. Posting into 404s spends the one act of promotion the plan allows, and it is not
recoverable — a Show HN cannot be resubmitted.

Measured, dated, and decided in the same hour as the measurements: 2026-08-16.
